# 루틴: 주간 앱 점검 (기획 파트너)

- 일정: `CRON_TZ=Asia/Seoul 45 7 * * 1` (매주 월요일 07:45 한국 시간)
- 실행 방식: **기획 파트너 세션(🧭 기획 파트너)에 매주 메시지로 깨워 넣는다** (persistent session).
  - 왜: "실행마다 새 세션" 방식은 루틴에 저장소 쓰기 권한이 붙지 않아 푸시가 403 으로 막혔다
    (2026-10-02 시험 2회 모두 실패, add_repo 로도 안 됨). 기획 세션은 저장소가 붙어 있어 푸시가 된다.
  - 새 계정에서 복구할 때: 저장소를 붙여 새 세션을 열고(= 새 기획 파트너), 그 세션 안에서
    "이 세션으로 주간 점검 루틴 만들어줘"라고 하면 된다 (create_trigger 기본값 = 이 세션으로 깨우기).
- 처음 만든 날: 2026-10-02

## 프롬프트 원문

```
[주간 점검] 월요일 아침 주간 점검 시간이다. 이 세션(🧭 기획 파트너)에서 진행한다. 사용자는 출근길에 폰으로 본다 — 한국어로 짧게.

1. `git fetch origin` 후 main 을 최신으로 받고 `CLAUDE.md`·`PRODUCT.md` 를 다시 읽는다 (다른 세션들이 그동안 바꿨을 수 있다).
2. `board/` 전체를 읽고 각 앱 세션의 상태·사용자 피드백·막힌 것·노하우를 파악한다. 여러 앱에 통하는 교훈은 `PLAYBOOK.md`·`board/_shared.md` 로 옮긴다.
3. 지난 7일 변화: origin/main·원격 브랜치 최근 커밋(research 봇 제외), GitHub Actions 최근 실행 성공/실패.
4. 앱별 현황 정리(PRODUCT.md 3장). 확인 못 하는 것(심사 결과, AdMob 수익, 리뷰)은 추측 말고 "확인 못 함 — 사용자 확인 필요".
5. 트렌드 조사: 웹 검색으로 이번 주 미국 App Store 상위·급상승 앱, 광고로 도는 캐주얼 게임·유틸 중 작게 빨리 만들 수 있고 광고 수익이 날 후보 2~3개 (출처 링크). 선교 현지에서 쓸 만한 아이디어는 따로 표시.
6. PRODUCT.md 갱신: 3장 표, 4장 백로그, 8장 `<!-- 주간 점검 기록 -->` 바로 밑에 `### YYYY-MM-DD` + 지난주 한 일 / 막힌 것 / 트렌드 후보 / **이번 주 결정할 것 2~3개(A/B)** / 추천 작업 순서.
7. `PRODUCT.md: 주간 점검 YYYY-MM-DD` 로 커밋 → 작업 브랜치 푸시 → main 반영 푸시. 실패하면 실패라고 보고.
8. 답변: 이번 주 결정할 것(A/B), 추천 작업 순서, 확인 못 한 것 + GitHub Pages 링크.

코드 개발은 하지 않는다. 점검·조사·기록만.
```
